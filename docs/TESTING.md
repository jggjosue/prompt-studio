# Automated testing

## How it's set up

The project uses the **native Node test runner** (`node --test`), without Jest or Vitest. The reason is concrete: business logic lives in pure modules in `src/lib`, which are imported and tested without a DOM or extra transpilation —`tsx` resolves TypeScript on the fly—. Adding a full framework would have meant configuration, dependencies, and a second module system without solving any problem that exists today.

Three levels, each with its purpose:

| Level | Where | What it covers | How it runs |
|---|---|---|---|
| **Unit** | `tests/unit/*.test.ts` | Business rules, transformations, authorization, source code-level API contracts | `node --import tsx --test` |
| **Data** | `tests/data/*.test.mjs` | Catalog integrity: valid JSON, unique identifiers, existing media | `node --test` |
| **End-to-end** | `tests/e2e/*.spec.ts` | Real browser user journeys, keyboard accessibility, and performance budgets | Playwright |

## Commands

```bash
npm test                 # unit + data
npm run test:unit        # unit only
npm run test:data        # catalog integrity only
npm run test:coverage    # unit + data + lcov report
npm run test:e2e         # Playwright (requires PLAYWRIGHT_BASE_URL)
npm run test:e2e:performance   # Core Web Vitals and network budgets
npm run validate         # lint + types + coverage + .env.example + cache
```

To measure against a real deployment:

```bash
PLAYWRIGHT_BASE_URL=https://www.prompstudio.com npm run test:e2e:performance
```

## Coverage

`npm run test:coverage` produces **`coverage/lcov.info`**, the format read by Codecov, SonarQube, and repository evaluators.

The report is generated by [`scripts/mjs/build-coverage-report.mjs`](../scripts/mjs/build-coverage-report.mjs), which exists for two reasons that the native flag does not solve:

1. **Tests run in two processes** (unit tests with the `tsx` loader, data tests without it). Each writes its own lcov and the second would overwrite the first, so they are concatenated.
2. **`--experimental-test-coverage` only counts files loaded by tests.** Measured on this repository: 62 out of 676 modules. Reporting 93% on that sample would be misleading, so the script **completes the report with modules that no test imports**, declared with zero covered lines.

Results as of September 11, 2026:

```
Line coverage on src/: 5.48% (4,290/78,351)
  files with measured coverage:            62
  files with no test loading them:        614
```

That figure is low, and it is real. The previous one —93.87%— measured only the favorable portion.

### Threshold

```bash
COVERAGE_MIN=10 npm run test:coverage    # exits with code 1 below 10%
```

The threshold is passed via an environment variable instead of hardcoding it to allow raising it in CI as coverage increases, without touching the script.

## What is tested and why

Tests are written around what **breaks the business if it fails**, not what is easy to cover:

| Area | Examples of what is checked |
|---|---|
| **Authorization** | That the visual builder requires an account **and** plan on the server; that API routes return 401 and 403; that queries filter by `userId` |
| **Commerce** | Affiliate commissions, hold period for refund windows, purchase validation, generation pricing |
| **AI Generation** | Output contracts, job queues, evaluation suites, human preferences, provider quality |
| **Visual Editor** | Nesting rules, cycles when moving a node inside itself, style inheritance per breakpoint, full undo/redo round-trip |
| **Catalog** | That paid fonts remain publicly inaccessible, identifier integrity, asset provenance |
| **UI** | User journeys, keyboard navigation, Core Web Vitals budgets |

A principle that is applied and worth making explicit: **verify that the test detects failures, not just that it passes**. The `.env.example` guardrail was validated by copying four real secrets into the file and verifying that it flagged them.

## Structure

```
tests/
  unit/     *.test.ts   — one test per module or contract
  data/     *.test.mjs  — integrity of versioned catalogs
  e2e/      *.spec.ts   — Playwright journeys
```

Test names describe the expected behavior, in Spanish, exactly as read in the runner output: `la API conserva identidades privadas y evita el patrón N+1`, `un drop con índices imposibles no rompe la lista`.

## Requirements

- **Node ≥ 22.11** (see `.nvmrc`). `preinstall` checks this.
- Do not mix arm64 and x64 installations in the same `node_modules`: the SWC binary stops loading.
- Playwright needs its browser: `npx playwright install chromium`.

## What's missing

With 614 modules lacking any test loading them, priorities are clear and in this order:

1. Business modules already measured but weak: `component-purchase-validation` (23%), `generation-pricing` (49%), `affiliate` (61%).
2. API routes: currently checked at the source code level (that they call `auth()`, that they filter by `userId`), not by executing them.
3. React components: no render tests.
